# 生成拆纵向切片 run + URL 事件驱动推送（渐进预览 v2，修订 #42 刷新单元口径）

渐进预览（#42 定、#90 已落地 b 档⑤）实测不达「做一点展示一点」：预览全程 503、收口时整个系统一次性砸出来。本 ADR 激活 #42 Further Notes 留的后门（「若实践中发现一步跨太多导致跳变过大，再评估更细粒度」），把生成的刷新单元从「一次完整修改」修订为「一个纵向切片收口」，并连带修正 URL 获取路径。

## 问题：两个割裂，一个不成立

- **URL 从不推送**：`preview-ready` 事件带 URL，却只在 REST `preview()` 成功后作为副作用发出（前端不轮询成功它永不来——鸡生蛋），且前端对它**空登忽略**（bridge 注册表 `preview-ready: []`，非载荷写入口）；步骤探活发的 `preview-updated` **不带 URL**，前端只拿它 bump 纪元重挂「已缓存的 URL」。于是 3s 轮询成了拿 URL 的**唯一**路——事件驱动的「刷新」与「拿 URL」两套机制割裂。
- **执行体不「先起服」**：8081 只在收口探活那一刻可达（`CLOSING_PROBE` curl 8081）。#42 的步骤刷新机制（`StepBoundaryPreviewRefresh`：步骤边界探活→过则发 `preview-updated`）建立在「执行体在段中已经起服」这一假设上——假设一破，探活每步都未过、机制全程空转，预览停在占位直到收口。

两处同一条因果链：**预览可见性 = 8081 何时可达**；而现在 8081 只在收口时可达，且可达了也不推 URL。

## Considered Options

- **单 run 内强化「先起服」（在 #42 机制内修 prompt）**——出局：先起服目前是三层纯 prompt（`GENERATE_RUN_PROMPT` / EXECUTOR 第 4 条 / 工作区 AGENTS.md），执行体不遵循；平台侧只有收口探活一个观察点，无早期硬检查点能强制「先起服」。单 run 的黑盒窗口 = 整个系统，不可靠性不因 prompt 加码而收窄。
- **拆水平层（骨架 / 前端 / 后端 / 数据分阶段）**——出局：每一层都不是「用户可操作可观测的完整点」，预览见的仍是中间态（空表、无前端、工作区文件列表），违背「做一点展示一点」。
- **拆纵向切片 run**——选定：每个 run = 一个从前端到后端完整走通、用户可操作可观测的点（垂直切片）；首段先起服空白页，此后逐片加厚。刷新单元随之从「一次完整修改」改为「一个切片收口」——平台确定性检查点，不依赖执行体自律。
- **URL 获取：保持 3s 轮询 vs 事件驱动推送**——选定推送：切片收口（及首片探活首次通过）发 `preview-ready`（带 URL），前端消费写预览查询缓存；3s 轮询降级为 SSE 断线兜底。

## Decision

1. **生成从「单 run 一次长全」改为「先起服 + 纵向切片逐段」的多 run 轨道**，复用 `IterationAppService.runFixTrack` 的「轨道顺序多 run」模式（该模式已在修正侧验证）。
2. **切片单位 = 纵向的用户可操作、端到端走通的点**（如「用户能登录并看到自己的订单列表」= 登录页 + 鉴权 + 订单表 + 列表接口 + 列表页，一段走通）；不按水平层、不按功能数凑段。
3. **阶段 0 = 系统初始化骨架（先起服）**：最小可运行形态上 8081，收口即空白页（白底）——这是唯一的水平工序，解决「全程 503」；此后切片逐段长出系统。
4. **切片计划由主智能体产出**（职责延伸：需求侧才知道哪些能力该捆成一个用户点、什么顺序自然），平台只顺序执行、不解析自由文本。
5. **URL 事件驱动推送**：`preview-ready` 由切片收口（及首片探活首次通过）发出并携 URL，前端消费写进预览查询缓存；3s 轮询降级为 SSE 断线兜底。

## Consequences

- **切片计划**：主智能体在产出 PRD 后顺带产出有序切片计划（每片一句用户语言描述「用户能 X」），作为生成编排的输入；切片数量是 PRD 切片结构的涌现结果，不是平台旋钮。职责判定归主智能体，平台不新增「解 PRD 结构」的解析面（能代码不 LLM 的边界：不解析自由文本）。
- **每片收口判据**：该片能力用户可操作（执行体 `self-test` 子智能体验证走通）+ 8081 常驻 + 版本 commit（复用 #91 收口自动成版）+ `run-finish` 推 `preview-ready`(URL)。平台侧检查点仍是「8081 可达 + 成版 + 事件」，「端到端可操作」由片内 self-test 兜——与现有收口探活/自测口径同源，不新增探针。
- **刷新单元口径修订**：`#42` 的「一次完整修改（步骤边界探活）」改为「一个纵向切片收口」；`StepBoundaryPreviewRefresh` 的步骤边界刷新退役（其假设已证不成立，切片收口是更可靠的检查点）。`#90` 的验收口径「占位→首跑可用→渐进显现」由「阶段 0 收口→切片逐段收口」承接；`preview-updated` 通知的逐修改刷新链路随之退役。
- **URL 推送机制**：`preview-ready` 从「REST preview 成功后的副作用」改为「切片收口/首片探活首次通过」发出；前端 bridge 从空登改为载荷写入口（`setQueryData` 写预览查询缓存 URL），消掉自反馈循环顾虑（写缓存非失效，不会重拉 preview 再发事件）。
- **失败语义**：某片 run 失败走既有静默重试/超限终态（`run-failed`），不自动跳下一片——「做一点展示一点」的完整性优先，失败片要在预览里可见地修复；用户重提即兜底。
- **`generated_at` 口径不变**：仍落最后一片收口（首次生成时点），「确认下单」可见性口径不因拆片漂移；拆片期间的对话意见照旧止于对话（未生成不派更新 run）。

## 未来增强（备案，带触发器）

- **预览跟随修改位置**（切片内定位到正在修改的路由/元素，含弹窗定位）：需要执行体新增「正在改哪个路由/元素」的结构化信号 + 平台把信号映射到 iframe 导航/滚动/高亮（弹窗还要在生成的系统里注入触发）。`#42` Out of Scope 已押后「直播页面级结构化事件与预览的强制联动」，本项是其细化。**触发器**：切片级可见性落地后，若切片内仍觉得「看不到具体改在哪」再评估；先看实际效果再议。中间档「切片收口后预览跳该片落地页」若需，一并届时裁量。
