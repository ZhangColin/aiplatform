# 并行宽度实测：依赖图理论宽度 vs 调度实际宽度（#409）

调研日期 2026-11-06。数据源：生产库（eu-1 semgravio-pg，只读 SELECT）`prj_generation_segments`（V41 后带 `depends_on` 的全部 7 个项目——这是全量普查不是抽样）＋ `prj_conversation_entries`（kind=5 收尾卡：`created_at`、`closing->>'durationMs'`）；代码面 `aiplatform-server`。

## 结论（三行版）

1. **调度器不保守、无并发上限问题**：7/7 项目「实测最大并发 = 依赖图理论宽度（最大波宽）」，同波起跑离散 ≤0.2s（真并行）；线程池 8（`SliceParallelExecutor.THREADS`）从未打满，生产实测过宽度 6（项目 374099250485075957，6 片同波）。
2. **宽度窄的主因是依赖图本身**——主智能体产出的切片计划是真实产品域链（录入→学习→测试→报告），宽度只有 2-3；提示词已要求最小依赖（`MainAgentAppService` L422-425、`SaveBuildPlanTool` description），星型计划的存在证明模型并非只会链式声明。
3. **票面二分法之外的第三因素：波栅栏（barrier）语义**——波内最慢片收口前，只依赖波内快片的下一波片干等。同依赖图换就绪队列（ready-queue）调度：锚 105m40s→93m02s（-12m38s）、376641550051648839 121m17s→110m17s（-11m）、374391067239046747 56m08s→50m26s（-5m42s）；纯链项目（374150839275879478、374842388277664258）无收益。

## 一、调度机制（代码事实）

- 分层：`SliceSchedule.parallelWaves`——首片固定 0 层恒单独跑（界面先行、预览先活）；片 2..N 层 = 1 + max(依赖片层)，无依赖 = 1 层。**同层（波）并行、层间串行（栅栏）**。首片/阶段 0 不进波。
- 执行：`GenerationAppService.runParallelWave`——波内先全部提交再统一等待（`sliceParallelExecutor.submit`，池 8 线程 daemon），落定后**按 ord 序逐片合并**（`mergeFork`：fork diff → `git apply --3way` 机器查冲突 → 冲突转子智能体裁决 → 主工作区成版），波末统一探活主工作区＋推预览。**单片波退化主工作区串行（无 fork）**。
- 失败/停止：失败片跳过不拖垮其余片（#351）；停止全释放本波 fork（#359，登记簿 `createdForks`）。
- 合并冲突兜底：裁决 run（`coder-{projectId}-merge-{ord}` 会话）＋失败回滚主工作区到 merge 前 HEAD（#353）。

## 三、锚案例（376467559906353574）拆解

依赖图（生产库 depends_on 原样，片义见 `prj_generation_segments.description`）：

```
阶段0(系统初始化) → s1(双端界面骨架) → s2(注册登录) →┬→ s3(打字录词) →┬→ s4(OCR录词)
                                                     │                └→ s5(单词本管理) → s6(学单词) → s7(选择题测试) →┬→ s8(拼写/听力题)
                                                     │                                                   └→ s9(复习提醒) → s11(家长进度报告) → s12(时长统计)
                                                     └→ s10(家长绑定孩子)
```

- 时间窗重建的实际重叠对：**s3/s10、s4/s5、s8/s9**——与波 [3,10]、[4,5]、[8,9] 一一对应（票面写的 s3/s4、s5/s6、s9/s10 是对名出入，「3 对、宽度 2」结论不变）。
- 关键路径 90m47s（链 0→1→2→3→5→6→7→9→11→12）；实测净生成 105m40s；全串行和 137m57s。
- **105m40s − 90m47s ≈ 14m53s 里，约 13m44s 是波栅栏空等**：s11 只依赖 s9（05:45:43 收口），但波 [8,9] 要等 s8（2028s 波内最长片，05:59:28 收口）合并完才放行（05:59:34 起跑）。真正的编排开销（合并/fork/探活）合计只有 ~66s。
- 依赖声明**不过分保守**：链是真实数据依赖（单词数据 → 学习 → 测试 → 家长报告），s10（家长绑定）已按独立分支挂 s2。提示词侧已明确「无依赖的独立切片不写依赖（平台会并行生成它们）」。

## 四、差距来源判定（票问 1 的回答）

## 五、拓宽到 3-4 的工程清单与风险面（票问 2）

**现网冲突基线**：7 项目 45 次 fork 合并 **0 冲突**（18 个多片波的全部波间转场 ≤48s 干净收敛——冲突裁决是分钟级子智能体 run，不可能藏在 48s 里；收尾卡无任何「合并冲突」记录）。

### 工程清单（按性价比排序）

1. **去波栅栏：ready-queue 调度**（不碰依赖声明，锚类项目 -9~13%）。改动点：`GenerationAppService` 波循环 → 就绪队列（片依赖全收口即起跑）；合并改逐次排队（合并须主工作区空闲，与主工作区在跑片段互斥）；`createdForks` 登记簿生命周期从「波」延到「轨道」；末片收口补落（#355）与全片收口门槛逻辑改按全局闭片集判定。
2. **统一 fork 口径**：ready-queue 下「单片波退化主工作区」会成为隐性串行化点（主工作区互斥）——有多片就绪时全部走 fork，主工作区只在无并行机会时直跑。
3. **计划宽度反馈环（可选）**：平台算计划波宽，片数 ≥6 而宽度 <3 时把「依赖最小化」反馈给主智能体重产。**边界：依赖是正确性事实（共享页面/数据结构/登录态），不能为并行压依赖**——压掉的依赖会以合并冲突的形式还债。
4. **观测补缺**：fork 片改动文件集现在不落档（fork 收尾卡 files 恒空——`closeForkSlice` 只核验不落档），导致本次「拓宽后冲突率」只能靠时间窗间接推断。建议 fork diff 文件清单落收尾卡或事件面，作为冲突率的前置预测器。
5. **宽度遥测**：轨道级记录每波并发数、ready 等待时长、单次合并耗时、冲突裁决触发次数——没有这个面，后续任何调度改动都无法回归验证（本报告方法＝事后从收尾卡时间窗重建，可用但粗）。

### 风险面

- **冲突率**：0/45 是宽度 2-3 的经验。宽度 4 ＋ ready-queue 下 fork 基线更旧（fork 时前序片可能尚未合并）→ diff 漂移更大 → 3way 冲突概率上升。兜底链完整（机器查→裁决→回滚），但裁决 run 分钟级、会吃掉并行收益；建议先以冲突率遥测（第 5 条）为灰度门槛。
- **合并序语义**：现状波内按 ord 合并、基线统一（同波 fork 自同一主 HEAD）。ready-queue 下「新基线 fork」与「旧基线 fork」交错合并，patch 上下文失配面变大；合并序仍按 ord 但须处理基线不一致片的三方基准选取（fork 时的 HEAD vs 合并时主 HEAD）。
- **计量**：并发 4 = 4 路模型流同时跑，费用速率 ×4（总量近似不变）；`durationBreakdown.attempts[].modelId` 已按尝试计量、`UsageDims` 按 projectId+seat 维度在（`CoderRunAttempts` L432）；宽度 6 的 6 路并发在生产已发生过，未见计量/限流事故。
- **资源**：每 fork = 完整工作区容器（Node+PG+Redis 同容器）。eu-1 单主机 8 vCPU / 31.7GB，闲态可用 28.1GB；宽度 4 ≈ 主工作区+4 fork，宽度 6 已验证可承载（10-29 P1）。瓶颈更可能在主机磁盘 IO（多容器 PG 同卷）而非内存，建议遥测加容器资源采样。
- **预览/收口语义**：fork 期间主工作区不动、预览滞后窗口随波变宽变长（现状波末统一推送）；ready-queue 逐次合并反而让预览更及时，是改善项。#359 停止清理、#353 回滚基准在 ready-queue 下的事件序需要重推演（停止时在途 fork 跨「波」存在）。

## 附录：方法与局限

- 时间窗口径：run start ≈ 收尾卡 `created_at` − `durationMs`（durationMs = 首试起跑到收口，`CoderRunAttempts` L790）；片间编排（合并/fork/探活）不在窗内，恰好让波间空隙可直接量出合并+fork 成本。
- makespan = 首片窗起点到末片收尾卡时刻；CP 按真实 durationMs 沿 DAG 最长链求和；ready-queue 反事实用转移开销 15s/片（取实测波间空隙中位数量级）模拟，无限工人。
- 局限：①仅 7 个 V41 后项目（V41 落地于 10-29 前后，此前计划无依赖列）；②冲突率靠时间窗间接推断（fork 文件集不落档）；③「依赖是否可再压」没有 ground truth（需 fork diff 文件重叠分析，本次数据面做不到）。
- 复算脚本逻辑已随本报告入库于文中表格；原始查询均为只读 SELECT（生产库未做任何写操作）。
