# 工作区卷共性去重：硬链种子＋基座自动演进（原型闸门判红·实施冻结中）

工作区卷共性去重主干方案定档与度量口径正本（承 #474 2026-11-13 实施规格；调研正本：`docs/research/2026-11-13-pnpm-store-and-readonly-node-modules.md`〔pnpm 官方语义〕与 `docs/research/2026-11-13-hardlink-seed-probe.md`〔硬链探针原型〕）。问题陈述：每置备一个工作区卷都把镜像内构建好的基座工程（node_modules ~600M＋pnpm store ~600M）整棵字节级复制进独立卷，随项目数线性放大（eu-1 实测 15 个在册工作区卷 ~19.5G 纯冗余，96G 单盘用掉近半）；长尾闲置卷随演示项目累积。约束：置备速度与生成体验（ADR-0013 初衷）不回退，`pnpm add`/`shadcn add` 增量装包行为不变，本地开发环境（live 车道所在）必须继续可用，环境漂移早失败不静默退化。

## 原型闸门判定（#491，2026-11-13）

实施第 0 步＝四假设探针闸门，判定结论：

| 假设 | 判定 | 关键数字（探针报告） |
|---|---|---|
| ① 跨卷硬链成立性（含 golden 只读挂载 link 行为） | **红（本地）/ 生产待实测** | 容器内 ln 跨卷 **EXDEV**（`st_dev` 双侧同为 2096、同 superblock `8:48 ext4 /dev/sdd` 仍拒）；同卷双挂载亦 EXDEV——隔离粒度＝**每挂载**（Docker Desktop idmapped mount 行为，#491 以 busybox 双卷 ln 复验一致）；golden `:ro` 挂载时 link 同错（且只读写正确被拒）；VM 侧直连（`/mnt/docker-desktop-disk/...`）**成功**（同 inode 1795900、nlink=2）——ext4 层跨卷硬链合法，阻断只在容器挂载层。生产 eu-1 原生 dockerd 卷为普通 bind、**预期成立但须实测**（一条 ln 即可判） |
| ② `cp -al` 种子速度与 df 零增量 | 绿（同挂载几何） | 全量实拷 `cp -a` **10,348ms / +1,360,648K** 对照；`cp -al` **2,328ms / +30,112K**（≈2.2%，全部为目录块/目录 inode，文件数据零增量）；1.36G 种子秒级 |
| ③ 种子后 `pnpm add` 增量正常＋可变元文件清单 | 绿（条件：实拷断链） | `pnpm add left-pad` rc=0、**5,079ms**、`reused 591, downloaded 1`——非全量重装；golden 侧被原地串写的既有文件**恰好 1 个**＝`node_modules/.pnpm-workspace-state-v1.json`（同 inode 1838783、nlink 仍=2、O_TRUNC 原地改写）；`.modules.yaml`/`.pnpm/lock.yaml`/`.bin/*` 等均为 rename 语义天然断链；防御性实拷断链集 **≤3 文件 ~260KB**；新增字节全落 ws 侧（df +712K） |
| ④ symlink 农场解析正常 | 绿 | `pnpm exec next --version` → Next.js v16.3.1 rc=0（1,394ms）；`require` 解析 16.3.1/1.3.0 正常 |

**闸门结论＝红**：承载假设①在本地 Docker Desktop（WSL2 后端）容器内**确定不成立**，而「本地开发环境与新机制完全兼容、live 车道照常可跑」是规格硬约束（用户故事 19）——机制无法在本机承载，静默降级为全量实拷又违反「环境漂移早失败」约束（用户故事 20）。生产 eu-1 原生 dockerd 预期成立但本仓无生产操作权、未实测。按 #474 闸门协议：判定结论落档（本 ADR＋两报告），**#474 重开候选评估，下游 #492-#496 全部冻结**；eu-1 一条 ln 实测或机制几何重议（退路＝同卷 golden 几何，报告 §5.3）为解冻前置。

## 决策（承 #474 定档；冻结解除后实施，几何细节以重开评估为准）

**机制＝硬链种子**：基座 node_modules＋store 每镜像版提取得 **golden**（全局一份，单次 `cp -a` 同拷两树保住镜像内既有的 node_modules↔store 硬链共享，唯一内容 ≈691M 而非 1.36G——探针 E0 附带发现）；置备/深度唤醒/fork 造新卷时 helper 容器双卷互挂 `cp -al` 硬链种子进卷＋对可变元文件集实拷断链（初判集：`node_modules/.pnpm-workspace-state-v1.json` 必须实拷；`.modules.yaml`＋`.pnpm/lock.yaml` 防御性同拷——rename 语义是 pnpm 10.28.2 在 `add` 下的实测行为，不担保其它操作/工具）。种子后卷内布局与今日逐字节同构，运行时零改动，`pnpm add`/`shadcn add` 命令与环境不变。镜像 0.18 腾空镜像内工作区挂载点（基座 store 挪出工作区路径，堵 Docker 新卷首挂自动灌入通道），DEV_IMAGE 常量随版 bump、golden 按版创建/退役。

**基座自动演进（修订 ADR-0013「存量不回补」口径）**：基座版本跟随当前 DEV_IMAGE，**翻转只锚定在闲置→重建边界**——休眠前提即闲置，深度唤醒/强制重建时落到当前镜像版基座；**run 在途永不翻转**。修订理由：demo 阶段工作区承载的是测试数据而非用户生产数据，翻转风险由「幂等重建自愈」既有哲学吸收（工作区本就可随时销毁重建，ADR-0016）；「存量不回补」在逐字节整拷时代等于「永不演进」，会把基座版本锁死在首置备时刻、靠执行体绕行累积兼容债。收紧条件：进入生产数据阶段（用户真实数据承托）回头评估，届时翻转边界另行论证。ADR-0013 原备案（多栈演进＝一个栈一套镜像）不受影响。

**度量口径（du≠df）**：硬链使每卷 `du` 仍显示 ~1.2G（全量计价，属预期不是超标）；真实磁盘占用以 **df 增量/唯一 inode 字节** 为准。验收：新生卷共性固定成本 ≤150M（探针实测目录元数据 ~30M ≈2.2%，余量充足）；度量程序以探针 E2 步骤（df 前后对照）为可复用口径，后续回归对比同法。

**golden 缓存语义与重建程序**：golden 是**缓存不是资产**——硬链被原地写穿可能污染 golden（与 pnpm store 同类危害，假设③断链集即为防御），置备侧不加校验；golden 按镜像版创建/随版退役，多版本不积压。被污染或疑似污染时一键重建：从对应版镜像提取基座（单次 `cp -a` 同拷 node_modules＋store 保住层间硬链共享）→ 换新 golden 卷 → 旧卷点名 `docker volume rm`（绝不 prune；回收走收编通道准绳，ADR-0045 体系）。

**环境前提显式断言**：「所有 docker 卷同一后备文件系统」为硬性前提（st_dev 一致），且按探针结论收紧为「**目标环境的容器挂载层不隔离跨挂载硬链**」——置备路径上显式检查、早失败不静默退化（#491 实测：同 st_dev 在 Docker Desktop 挂载层仍 EXDEV，单验 st_dev 不足）。

**配套（不依赖闸门）**：封存阈值 30d→14d 纯配置收紧；存量 15 卷机制上线后批量封存回收（既有手动沙箱动作的运营批量，零迁移代码）；封存包形态与互斥语义不变。

## Considered Options

- **基座不落卷（pnpm 引用镜像层 store）**——验尸出局：镜像层预置 store 供热链接被 pnpm 官方文档数据否定（overlayfs copy-up，一次安装 copy-up 36.7k 文件/366MB）；只读 store 官方形态 frozenStore 只覆盖离线 frozen-lockfile 安装，无法承接 `pnpm add`（调研报告 1.6/4.5）。
- **共享 store 卷（多容器挂同一可写 store）**——验尸出局：信任域＋并发锁在 store 外（各容器 /tmp 独立互不等待，竞态）；store server 官方已删；virtual store 不可多项目共享（pnpm 官方定论）（调研报告 4.1/4.2/4.6/1.4）。
- **overlay/FUSE 挂载（含 pnpm GVS/mount-modules）**——验尸出局：GVS 实验期且 links 来自镜像层踩 EXDEV（#14504）；enableModulesDir=false＋FUSE 为实验 CLI、Linux 专属；overlay 上层层 copy-up 使「硬链」名存实亡（调研报告 2.4/4.5/5.2）。
- **封存阈值再调（候选 4）**——已采纳为配套项，但只收敛长尾、不解决新生卷线性放大，独担不了主干。
- **golden 与工作区同卷几何（#491 判红后的退路）**——机理数字成立（E2/E3 即按此验证）但 golden 冗余份数＝并发工作区布局策略问题，且与「golden 全局一份」用户故事冲突；仅在 eu-1 实测亦隔离时启用（调研报告 §5.3）。
