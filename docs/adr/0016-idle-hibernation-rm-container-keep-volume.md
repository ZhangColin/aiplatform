# 闲置休眠：删容器保卷的单一语义

随并行项目增多，常驻沙箱容器的内存/CPU 占用成为真实瓶颈（本机约 30 个容器即不可用，生产必现）。决定闲置休眠采用单一语义：睡即删沙箱容器（docker rm -f）保卷，醒即走既有幂等重建路径（重建容器 → 中间件自愈 → 8081 应用进程拉起 → 探活通过），不引入 docker stop/start 原语。唤醒编排顺带吃掉 #168 遗留缺口——应用进程不随容器自愈的问题由唤醒统一解决，不再另票。

## Considered Options

- **stop/start + 删除的两层管理**（stop 层回收 CPU/内存、删除层回收存储）：被否。删容器几乎不省存储——容器读写层无物，存储大头是卷内可重建缓存（node_modules / .pnpm-store / .next，GB 级）；stop 的恢复速度优势（亚秒 vs 重建数秒）被应用启动时间（10s+）淹没，且 stop 后容器内 pg/redis 进程全死、docker start 不复活，仍需拉起编排——两层换来两条唤醒路径、两套状态，收益为零。真正的存储回收走「封存」，见 Consequences。
- **平台侧裸 git 仓**（收口 commit 后 push 到平台本地裸仓，作为将来远端 git 服务器的同构前置）：被否。覆盖面只剩被 git 跟踪的代码，物料、数据库要另配导出路径，还要多管一套裸仓存储；卷瘦身快照最简且保全一切，远端 git 到位后封存包退位为一次性转运物。

## Consequences

- **意图/实态分离**：DB 只记期望态（运行/休眠）与 last-touch，不镜像 docker 实态；休眠器每轮以 docker 探查为准决策，漂移自动收敛（#168 事故教训：DB 记 ready、容器实死两天无人知）。启动期对账一次。
- **唤醒触发面 = 项目 API 自动唤醒**：后端统一 seam，复用置备待期口径与前端轮询；分享链接不做 lazy 拉起（访客走网关不触发，与 Replit 行为一致），网关定制「休眠中」页归体验线。
- **编排只依赖 EnvironmentBackend 端口与 DB 状态**：v1 单机 docker CLI 直连，不做多机/调度抽象；多机化或上云沙箱服务时换适配器，休眠策略与状态模型不动。
- **删卷只经「封存」，休眠永不删卷**：封存 = 卷瘦身快照（整卷 tar，仅排除 node_modules / .pnpm-store / .next 可重建缓存，**数据库随包**）存平台本地磁盘后删卷——项目文件卷外正本的本地方案先行，远端 git 服务器仍是长期正本方向。触发 = 后台手动 + 休眠满期自动（阈值可配，同时兼作 tar 全量恢复链路的验证手段）；重复封存覆盖旧包；封存与唤醒/删除互斥（in-flight）；项目删除时封存包一并清理。深度唤醒 = 重建 + 解包 + 自愈 + 应用拉起，分钟级，UX 仍是「系统启动中」。
- **归档与休眠正交**：归档是商业生命周期（归档项目仍可体验、后续业务还会扩展进去），休眠只看运行期活跃（last-touch 闲置计时，生成 run 进行中恒活跃）。
