# 单一主智能体对话，委派式执行（BA 并入）

平台智能体模型收敛为「主智能体 + run」两座：主智能体是与用户对话的唯一职能体（每轮一问的追问、答询、PRD 撰写修订、需求侧判定、发起 run），永不读写沙箱代码；构建变更全部发生在 run 内——执行体按五段循环（解读→探索→修改→自检→收口）干活，run 内设委派位（子智能体：自测、审查）与技能位（按需加载的能力包）两个一等挂载点。职能是配置不是结构：BA / 助理 / 编码智能体三个旧职能体词条退役（能力分别并入主智能体与 run 执行侧），角色卡、工具集、技能集均为可增配的数据。裁决依据（wayfinder #70，2026-09-04）：BA 为土制概念——行业六家无一设「与主对话并列的需求智能体」，需求梳理是主对话智能体的模式/交互卡（Lovable Plan 模式、v0 ask_user_questions）；行业的多智能体全部是主智能体/run 之内的委派（Lovable research subagents、Replit 自测子 agent、Kimi Swarm、扣子技能系统），不与主对话并列。本 ADR 修订 ADR 0004 假设的三职能体模型；0004 的核心——编排归平台代码、判定下放且机器可读——不变，仅判定座位搬家。

## Considered Options

- 保留 BA / 助理 / 编码智能体三职能体并列（出局：行业无同构物；「先访谈后开发」的隐性阶段感与无阶段论相悖——追问与构建连续于同一对话）
- 预编队团队：需求/设计/开发/测试多职能位并行协作（出局：行业实证为动态委派而非预编队；v1 无场景。扩展点保留——业务细化时加的是配置与子智能体，不是新结构）
- 独立 PRD 写作委派位（出局：随时间变细的是写作知识（模板/组织/写法），不是座位——由技能承载；且「对话→PRD」语境不干净，委派即再造交接损失带。文档族若长起来，文档职能委派位届时再议）
- 引入图引擎或 agentscope teams 编排原语（维持 ADR 0004 否决：结构仅两座+挂载点，用不上动态拓扑）

## Consequences

- 判定跟职责走不变，座位搬家：需求侧判定归主智能体、开发侧判定归 run 执行侧；机器可读判定契约与交接物机制照旧。
- 入口车道判定（意见/咨询/兜底，classify 轻调用）与项目取名（naming）保留为实现细节；车道语义不变（咨询零产物短路、挂起问答只拦意见链）。
- 用户面无角色标签（行业同构：六家用户界面均只有「the agent」）：role-assigned 帧与前端角色标签退役；过程呈现与对话呈现 parts 同源（wayfinder #64 口径）。
- v1 实现项排价于 wayfinder #66：BA 会话并入主智能体单会话、PRD 工具与判定契约搬家、PRD 写作技能搬家（角色卡→技能挂载点）、自测子智能体启用（需先解决子智能体工作区隔离——现为防交付物脏写而禁用）、挂载点机制就位。
- 技能来源三途：内置 / 自制 / 安装（市场技能；SKILL.md 生态同构，安装为扩展点）。
- 扩展点备案（带触发器）：自测子智能体（质量/预览自检诉求出现）、技能内容随业务长（首个=PRD 写作，内容即现有七章节模板）、市场技能安装、Swarm 级并行（单 run 时长成为体验瓶颈）。
