# 派发编排代码化，语义判定下放职能智能体

指令区输入的编排（意见链结构、分岔、终止、交接物组装、收口）由平台代码承载；语义判定只放两处——入口消息类型判定（意见/咨询/兜底）与职能体内职责判定（BA 只判要不要追问、要不要改 PRD；编码智能体只判要不要动系统），每个判定返回机器可读结果，编排按结果分岔（继续/跳过/终止/零产物短路）。咨询类输入由带工作区只读工具的助理职能体直接作答，不触发任何产物变更。

此前链路可靠性押在 BA 单次对话内连续工具调用上（savePrd 之后应再调 startFixRun），模型漏调即断链且无兜底——用户实测「把主色调改成绿色」只更新了 PRD、系统未动即此结构缺陷。判定跟着职责走，派发权不在任何职能智能体手里。

## Considered Options

- BA prompt 内自觉串联（现状，出局：单点漏调即断链）
- 独立 Leader 智能体全权编排（推迟：v1 不建，见下）
- 引入 spring-ai-alibaba graph 做编排层（v1 否决：整张派发图是一个入口分岔 + 两节点链 + 三种终止，用不上图引擎的动态拓扑/并行/checkpoint 能力，且与 agentscope-java 执行栈形成双栈成本；断链根因是判定契约缺失，不是路由写法）

## Consequences

- （#54 修订）排队语义扩到 BA 受理窗口：意见锚从 REST 线程 put 挪进会话执行器任务首行（同会话 FIFO 串行），BA 轮在途（REST 已返、收口未至）连发的意见各自成轮、各自收口派发，撞在途修正 run 走排队合并（#53）——「意见必达/不丢失」对受理窗口成立；converse 异常即清锚（对齐「收口即消费」，重提即兜底，不自动重试）。
- 入口类型判定点是将来 **Leader 编排智能体的种子**：平台方向是团队式多智能体协作（leader/需求/设计/开发/测试，一个指令指挥多个智能体按序/并行协作），智能体配置、管理后台、工作流编排是后续演进。v1 只留扩展点，不预支结构。
- 修正 run 的交接物 = 用户意见原文 + BA 判定结果（PRD 改没改、改了什么），二者缺一不可——摘要不能替代原文，原文不能让 CODER 自己从全量 PRD 猜关联。
- 「改 PRD 不必然动系统」：PRD 文档性修订是否落到系统，由编码智能体的开发侧判定裁量。
- 图引擎（spring-ai-alibaba graph 等）v1 不引入。重新评估的触发信号：编排图出现并行 fan-out 或动态拓扑、需要 run 级 checkpoint 断点续跑、自写路由复杂度失控。届时优先看 agentscope-java 自身演进出的编排原语（v2 源码仓已见 team/coordination 模块——Agent Teams 任务板+邮箱，尚未发版；subagent 的底层调用器是不承诺的内部 API，不可依赖），外部图引擎为对照候选。
