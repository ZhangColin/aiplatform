### 1. 上下文/token 增长曲线（压缩是否正常触发）

**曲线数据**（`target/rehearsal-434/usage-curve.csv`，剔除同会话槽位中 9 行冒烟残留后
279 次真实模型调用）：

| 指标 | 数值 |
|---|---|
| 首次调用上下文面积 | 3,102 tokens |
| 峰值 | 104,134 tokens（阶段 0 内，单 call 大工具结果注入 ~85K 所致） |
| 末次 | 20,999 tokens |
| 模型分布 | flash 146 次 / pro 133 次（文件数上涨后大标签片自然升 pro，路由行为符合生产口径） |
| 缓存 | run 内从早期 call 即命中（cache_read 2K→96K 复用普遍）；每派段首 call cache_read=0（新对话旁证） |

**压缩判定**：分析器（`RehearsalCurveAnalyzer`，半降规则）对原始 288 次调用报 **29** 次
半降事件——剔除 9 行冒烟残留后为 **28** 次，**全部是「新 run 开新对话 / verify 子智能体
切换」的边界假象，无一是框架压缩**（每事件后上下文
从 ~2-7K 重新起坡，正是新对话首 call 形态）。框架压缩真实触发 **1 次**：终态
`cat_agent_state.state_data` 含 `__compaction_summary__:5b948eb3-…` 标记（ord=3 片中），
摘要语义忠实——会话意图、基座铁律、前片结论（含「切片 2 登录未实际落地」）、环境踩坑
全部保留，压缩后对话照常推进。**压缩机制在长会话场景工作正常**。

**关键形态发现（对 #432 Step 2 设计直接相关）**：恒定 sessionId 复用的是
`cat_agent_state` 存储槽位，**不是对话窗口**——每次派段开启全新 agentscope 对话
（首 call cache_read=0、上下文 2-7K 起坡），跨段连续性完全靠 handoff 文本喂入
（大交接时首 call 达 30K）。即「同会话连续追加」今日语义＝槽位续用＋交接传递，
对话本体并不累积。单 run 内部可涨到 104K 不触发压缩（触发阈值/机理与纯 token 面积
不一致：104K 未压 vs ord3 ~35K 处压了 1 次），触发机理留作后续观测项。

### 3. 失败止损表现

| 段 | 尝试 | 终态 | 墙钟 | 备注 |
|---|---|---|---|---|
| ord=0 阶段0 | 1 | ✅ | 734 s | 118 calls，上下文涨至 104K |
| ord=1 | 2 | ✅ | 208 s | 第 1 尝试快速败后重试成功 |
| ord=2 | 3 | ❌ | 2,112 s（35 分钟） | **智能体自产 ①族违规命令挂死**（见下） |
| ord=3 | 1 | ✅ | 977 s | 含 1 次框架压缩；随后 60 分钟闸到点，ord=4 不再派 |

**止损链实证**：ord2 挂死后，活超时判死（工具执行窗 PT30M）终止该尝试 → 尝试环 3 次
耗尽 → 片失败 → **#429 续派生效**（ord3 照跑照收）→ 60 分钟墙钟闸到点**干净停派**。
整轨有收场、有数据、无悬挂。

**暴露的真问题**：ord2 的挂死源于**智能体自己生成的命令**含内嵌双引号
（`docker exec … sh -c "… grep -E "\.env|AGENTS|DESIGN" …"`）——Windows JVM→docker.exe
argv 编码链剥掉双引号后 sh 引号不配对，从 stdin 干等 35 分钟。即 **#399 ①族防呆
fail-fast 只罩平台自产命令，智能体经 ShellExecuteTool 下发的命令完全无守卫**；且工具
执行挂死期间常规沉默窗（PT10M）不生效，止损完全依赖 PT30M 工具窗——单次挂死吃掉
60 分钟预算的 58%。人工杀 exec 客户端后工具调用返回错误、链路可自愈，但为时已晚
（已被判死）。

## 三、go / no-go 决策建议

**对「60 分钟纯单会话承载锚需求全旅程」：NO-GO。** 依据：

1. **预算不够**：实测吞吐 stage0 12.2 min＋片均 ~8-16 min，60 分钟仅覆盖
   stage0+3/9 片（约 40% 旅程）；全旅程估 2.5-3 h。60 分钟单会话装不下全旅程，
   这是硬数据不是风险猜测。
2. **止损盲区未修不上长程**：智能体自产 ①族命令可无界挂死（本排练实测 35 分钟
   单点损失），PT30M 工具窗兜底代价太高。必须先补守卫（见四）再谈更长单会话。
3. **收口判定盲区**：「假完成」事件（登录片）在 4 段小规模即出现 1 起，旅程越长
   越难被后段自认摘要兜出。

**对 #432 Step 2「同会话连续追加」机制本身：GO（带条件）。** 本次排练验证机制要素
全部成立：会话槽位恒定续用、handoff 跨段传递、框架压缩长会话下工作正常且语义忠实、
#429 失败续派、墙钟闸干净停派。**建议形态＝2-3 段大块会话**（按实测 ~16 min/片
切分，每段 3-4 片，段间以 handoff 衔接——与今日每派段新对话＋交接传递的语义同构，
无需新机制），而非 60 分钟单会话硬装全旅程。

## 四、暴露问题与后续

1. **①族守卫盲区（最高优先）**：智能体自产 shell 命令无 ①族校验。可行路径
   （「换实现而非重开 offload」同理精神——在既有链路上补守卫，不新造通道）：
   - 短平快：系统提示层明确「容器命令一律单引号形态、禁内嵌双引号、禁 `$()`」
     （前片踩坑已有类似沉淀，见 ord3 摘要「环境限制」节）；
   - 根治：`DockerExecFilesystem` 执行前对智能体命令做与平台同口径的 ①族检测，
     违规即拒并回错误（让智能体改写重试），把 fail-fast 延伸到智能体面。
2. **收口闸需求真实性盲区**：建议 verify 子智能体对照 PRD 功能清单逐项登记
   （现有 report_verification 已逐项，但无「清单对照」锚），或 ClosingJudgment 增
   「需求覆盖声明 vs PRD」一致性抽查。
3. **压缩触发机理存疑**：104K 未压 vs 35K 压 1 次，阈值非纯 token 面积。建议框架
   侧补 compaction 事件落库/日志锚（现无任何观测锚，只能靠 state 标记旁证）。
4. 本排练产物：分析器 `RehearsalCurveAnalyzer`（纯函数＋4 例单测，fast lane 常绿）
   与 harness `SingleSessionLongRunRehearsalLiveTest` 已入库，可复跑
   （`REHEARSAL_434_CAP_MINUTES` 可调预算）。
