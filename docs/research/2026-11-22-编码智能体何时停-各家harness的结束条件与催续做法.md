# 编码智能体何时停：各家 harness 的结束条件与催续做法

- 日期：2026-11-22（调研执行 2026-11-21 至 11-23；2026-11-23 随 #590 决议落档，owner 已用作决策依据）
- 服务对象：本平台「一次生成 run 怎么结束」的决策——现行的结束条件与催续方式要不要改、改成什么形态。
- 背景：本平台现在一次 run 的结束条件是「模型连续两次回复都不带工具调用」，而且模型一停下来，框架就原样重发同一条消息「继续，直到完成 PRD 全部功能并在 8081 起服务」。实测（已对逐轮日志独立复测）：四次首建里，模型第一次说「做完了」都在第 9.7–12.3 分钟；[首建实测](https://github.com/ZhangColin/aiplatform/issues/576) 的三次此后又分别说了 38／25／48 次「做完了」，被这条消息推着又干了 10–23 分钟，约占一半到七成时间（按工具轮时长 48–67%），其中一次直到 300 轮上限才被切断；最早的一次（18 分钟基准）是被 150 轮硬上限截停的。owner 的问题：参考系统怎么处理这件事，有没有行业通行做法。
- 取证纪律：官方开源仓库默认分支源码＝**A 级**；官方文档＝**A 级**；官方团队成员公开发言＝**B 级**；社区多方一致＝**C 级**；社区孤证＝**D 级**。本报告全部引文为 A 级：开源系统按提交逐文件读源码（经 GitHub API 读取文件内容，不克隆、不执行），闭源系统只取官方文档（2026-11-23 抓取）。核实不到的事实写「未核实」，不猜。

- v0／Lovable／bolt.new 商业版的质量底线与自动修复，仓内已有调研，本文只引用不重做：[2026-09-03 benchmark](2026-09-03-benchmark-ai-app-builders.md)、[2026-11-06 Lovable 全能力面](2026-11-06-lovable-capability-deep-dive.md)、[2026-11-21 竞品风格与质量底线](2026-11-21-竞品生成器风格多样性与质量底线调研.md)。
- 用词约定（都是行业通用词，首次出现处给白话解释）：
  - **harness**：模型之外那一层代码，负责发请求、执行工具、决定一轮接一轮跑到什么时候停。
  - **一轮（turn）**：模型的一次回复；**一步（step）**：一次模型调用加随后的工具执行。各家叫法不完全统一，引用时保留原文用词。
  - **结束条件**：harness 判定「这次任务做完了、不用再调模型」的那个判据。
  - **催续**：模型想停下来时，harness 自动再发一条消息让它接着干。本报告关心的正是这件事的触发条件、消息内容、有没有次数上限。
  - **停止钩子（Stop hook）**：模型准备结束时先触发的外部脚本，它有权把模型拦回去继续。
  - **目标循环（goal loop）**：给这次任务设一个明确目标，每轮结束后判断目标是否达成，没达成就自动开下一轮。由谁判断各家不同：另起一个模型当「审核者」（OpenHands、OpenCode、Claude Code），或让干活的模型自己先对账（DeepSeek Harness、Codex）。

## 结论速览

1. **没有单一的「行业标准」，但结束条件只有两类主流做法，外加一类正在成形的做法。** 两类主流：①模型有一轮不调工具就算结束（Claude Code、Codex、Gemini CLI、OpenCode、Goose、Cline 的默认交互入口、bolt.diy 的默认模式、DeepSeek Harness 的默认）；②必须显式调用一个「提交／完成」工具或命令才算结束（Cline 的 `submit_and_exit`、Roo-Code 的 `attempt_completion`、OpenHands 的 `finish`、SWE-agent 的 `submit`、mini-swe-agent 的 `echo COMPLETE_TASK_AND_SUBMIT_FINAL_OUTPUT`、bolt.diy Agent Mode 的 `agent_complete`）。正在成形的一类是「有人把关」：模型说做完了不算数，得先对过账——服务端核对事实（bolt.diy Agent Mode 的完成闸门、SWE-agent 的提交后复核），或目标循环里另起一个模型当审核者（OpenHands／OpenCode／Claude Code），或让干活的模型自己先取证、再显式标记完成（DeepSeek Harness、Codex 的目标续跑）。
2. **「模型一停就自动催」是常见机制，但没有一家是无条件、无上限、固定一句「继续」的。** 查到的 13 个系统里，凡是自动催续的都至少占以下两条中的两条：只在特定情况触发（没调完成工具、空回复、输出被截断、审核者判未完成、有活跃目标）、消息带信息（缺什么、错在哪、第几轮／共几轮）、有次数上限或「没进展就停」（2／3／5／8／10／50 不等）。最接近本平台的有两个，也都有止损：Roo-Code 每次没调工具都注入同一段提醒，靠「连续错误 3 次」的上限兜底后问用户；DeepSeek Harness 的目标续跑每轮都发同一段模板，但有轮数上限（默认 256，提示里写明第几轮／共几轮）、要求模型显式标记完成、同一障碍连续 3 轮才能报受阻、且必须由人授权才续跑。本平台「不区分情况、不带信息、只靠 300 轮总上限兜底」的固定消息，在本次样本里没有对应物。
3. **所有自动续接都有小上限，而且几家把它定在个位数。** 输出被截断后的续写：bolt.diy 1 次、OpenCode 2 次、Cline 3 次、mini-swe-agent 连续 3 次格式错误即退出；停止钩子连续拦截：Claude Code 8 次、Goose 8 次、Cursor 默认 5 次；目标循环：OpenHands 最多 10 轮、Codex 连续 3 轮空转即停、OpenCode 最多 50 轮且连续 3 轮没进展即暂停、Claude Code「连续几轮不调工具」即停、DeepSeek Harness 默认 256 轮。
4. **步数／轮数上限普遍存在，默认值差别很大，撞上限后的表现分两派。** 默认值：OpenHands 500、Gemini CLI 单次调用 100（会话轮数默认不限）、Goose 1000、bolt.diy Agent Mode 32、DeepSeek Harness 目标续跑 256；Cline、mini-swe-agent、OpenCode、Claude Code 默认不限。撞上限后的表现：多数是「关掉工具、让模型写一份如实总结」（OpenCode、bolt.diy、Goose；DeepSeek Harness 记为「受阻：轮数用尽」后让模型写收尾说明；Codex 预算用尽时让模型收尾），少数直接以错误收尾（OpenHands `MaxIterationsReached`、Claude Code `error_max_turns`、mini-swe-agent `LimitsExceeded`）。
5. **「出错后自动修」在通用编码 agent 里是模型自己的行为，harness 不单独设重试次数。** 各家系统提示词普遍写明「测试失败就修、修完重跑」，框架层面只管两类硬上限：格式错误／被拦动作的重问次数（SWE-agent 3、mini-swe-agent 3）、原地打转的检测（Cline 连续相同调用 5 次、Gemini CLI 同一工具调用 5 次、Roo-Code 3 次、OpenHands 同参数同错误 3 次）。唯一把「构建／运行错误」做成专门入口的是面向网页应用生成的 bolt.diy，而且是用户点按钮才把错误发给模型，不是自动的。
6. **「完成前先验证」在多数系统的提示词里有明文，且写法高度一致：以工具输出为准、没证据不许说做完。** DeepSeek Harness 的续跑模板同向（'Before claiming completion, gather evidence that the whole objective is achieved'）。例外是 OpenCode 和 Goose，系统提示词里没有这类句子（开源源码一手）。闭源的 Claude Code 系统提示词不公开，未核实。

## 1. bolt.diy（网页应用生成器，main@72db5ce，2026-11-21）

bolt.diy 是样本里唯一和本平台同类（输入需求、产出可运行的网页应用）的系统，也是 2026 年变化最大的一个：它把「完成」从「模型自己说了算」改成了「服务端核对证据」。仓内 [2026-09-03 benchmark](2026-09-03-benchmark-ai-app-builders.md) 记录的是改动前的形态（输出截断即发 CONTINUE_PROMPT、流恢复 45 秒 2 次），以下是现行源码。

### 1.1 结束条件：两套并存

- **默认模式：没有完成工具，模型停止调用工具即流结束。** 默认模式下每一步的工具选择是 `toolChoice: 'auto'`，未见额外的完成判定（A 级，`app/lib/.server/llm/agent-loop.ts:171`）。
- **Agent Mode（2026-10-13 加入，默认关闭）：必须调用 `agent_complete`，且服务端核对通过才算完成。** 开关存在浏览器 cookie 里，默认值取 `Cookies.get('agentMode') === 'true'`，即默认关（A 级，`app/components/chat/Chat.client.tsx:221`）；用入门模板首建时自动打开，并走单独的 12 步上限（`MAX_STARTER_BUILD_STEPS = 12`，`app/lib/common/starterBuild.ts:12`）。闸门的判据是一组条件全部成立：有计划、计划之后有过编辑、编辑之后跑过应用、最近一次修改或失败之后有一次通过的检查、计划要求预览时预览在跑、没有未返回的工具调用（A 级，`app/lib/common/agentLoop.ts:245` 一带的 `completed` 表达式）。
- **闸门不过时，`agent_complete` 返回工具错误而不是结束**：`{ isError: true, completed: false, problems, … }`，`problems` 是具体缺项，例如 'Record a plan with explicit completion criteria using agent_plan.'、'Run the app or requested program and inspect the result.'、'Confirm a running preview.'、'Run a relevant test/check with purpose test and confirm exit code 0 after the latest edit or failure.'（A 级，`agentLoop.ts:282-299`）。

### 1.2 催续

- **默认模式：只在输出被截断时续写，最多 1 次。** 触发条件是 `finishReason === 'length'`；消息是 CONTINUE_PROMPT：'Continue your prior response. IMPORTANT: Immediately begin from where you left off without any interruptions. Do not repeat any content, including artifact and action tags.'（A 级，`app/lib/common/prompts/prompts.ts:6`）。`MAX_RESPONSE_SEGMENTS = 2`（`app/lib/.server/llm/constants.ts:42`），再被截断就抛 'Cannot continue message: Maximum segments reached'（`app/routes/api.chat.ts:453`）。源码注释说明这个上限以前因为计数器问题形同虚设，现已修好。
- **Agent Mode：三种带信息的催续，全部有上限。**
  - 该调工具却没调：'Your previous response did not call a required tool.'，最多 2 次（`MAX_RECOVERY_ATTEMPTS = 2`，`app/lib/.server/llm/agent-stream.ts:10,54`）；同时通过 API 参数 `toolChoice: 'required'` 强制下一步必须调工具（`agent-loop.ts:204`）。
  - 输出在工具调用中途被截断：'Your previous response reached the output limit before completing a tool call. Make one call with concise arguments and omit any preamble. For a large edit, make the first small, valid change in this call and finish the rest in later calls. Aim for about 10 lines of code in this call.'（`agent-stream.ts:53`）。
  - 闸门不过：把 `problems` 作为工具错误回给模型；每条待办指令的末尾都带进度提示 'Do not send a prose response while this action is pending. Remaining task steps: N. Confirmed: plan=…, edits=…, run=…, passing check after latest changes=…, preview=…'（`agentLoop.ts:347`）。
- **用户可见的进度提示**（不是发给模型的）：'The model missed a required tool call. Retrying the current step; completed work is preserved.'／'Provider response stalled. Retrying the current step; completed work is preserved.'（`api.chat.ts:326-327`）。

### 1.3 上限

- Agent Mode 任务步数 `MAX_AGENT_STEPS = 32`（`agentLoop.ts:12`）。到顶后状态变 `limited`，工具被关掉（`toolChoice: 'none'`），给模型的指令是：'The 32-step task limit was reached. Stop using tools and report actual progress, unmet completion criteria, and checks that did not pass.'（`agentLoop.ts:316`）。用户看到的是模型据此写的汇报（推断：该文本是发给模型的指令）。
- 闸门通过时同理关工具并要求总结：'The completion gate accepted this task. Summarize the relevant changed files, passing checks, and fulfilled criteria. Do not start unrelated work.'（`agentLoop.ts:320`）；模型被拒或受阻时：'Stop using tools. Explain the blocker or denied operation and list unmet completion criteria without claiming success.'（`:312`）。
- 入门模板首建：`MAX_STARTER_BUILD_STEPS = 12`，到顶同样关工具并要求 'Stop using tools and summarize the actual progress and unfinished work. Do not claim the requested app is complete.'（`starterBuild.ts:12,94-95`）。
- 每条消息内的工具步数：`stopWhen: isStepCount(agentLoopEnabled ? Math.min(maxLLMSteps ?? 12, 12) : (maxLLMSteps ?? 1))`（`api.chat.ts:359`）——Agent Mode 下最多 12 步／条，默认模式 1 步／条；界面上可调的 `maxLLMSteps` 默认 5（`app/lib/stores/mcp.ts:20`）。
- 流恢复超时：首字节／空闲 120 秒、单次尝试 300 秒（`agent-stream.ts:9`）；底层流重试 `maxRetries: 3, timeout: 30000`（`app/lib/.server/llm/stream-recovery.ts`）。

### 1.4 出错后怎么修

- **默认模式：预览或终端报错时弹出提示条，用户点「Ask Bolt」才把错误发给模型**，提示语 'We encountered an error while running the preview. Would you like Bolt to analyze and help resolve this issue?'（A 级，`app/components/chat/ChatAlert.tsx:18-19`）。不是自动修复。
- **Agent Mode：靠提示词要求模型自己修**：'Run the requested app/program, then the smallest relevant available checks. Inspect actual outputs and exit codes. If a check fails, patch its cause and rerun it; edits invalidate earlier passing checks.'（`app/lib/.server/llm/stream-text.ts:237`）。框架层不单独计修复次数，只有上面的 32 步总上限。

### 1.5 提示词里关于「做完」和「验证」的句子

- 'Do not claim a task or check is complete without tool evidence. Keep the plan focused on the user's request and do not invent extra work.'（`stream-text.ts:239`）
- 'Call agent_complete with successful tool evidence for every planned criterion. If blocked or the task limit is reached, clearly state unmet criteria and failed or missing checks.'（`:238`）
- 'Treat tool output as the source of truth. Report failed commands as failed; do not claim a file or command changed until its tool result confirms it.'（`app/lib/.server/llm/prompt-workstyle.ts:19`）
- 'Confirm a dev server's readiness from its actual output before claiming the preview is available.'（`prompt-workstyle.ts:17`）
- 'If no automated test script exists, use an available typecheck, lint, focused runtime assertion, or smoke check and explain its limits; do not invent passing tests. If work cannot proceed, report outcome blocked with a concrete reason.'（`agentLoop.ts:345`）

## 2. Cline（main@8075d2e，2026-11-21）与 Roo-Code（已归档，main@b867ec9，2026-05-15）

Roo-Code 是 Cline 的分支，两家的循环逻辑同源但已经分叉。Cline 现在是单仓库结构，循环在 `sdk/packages/agents/src/agent-runtime.ts`；Roo-Code 的循环在 `src/core/task/Task.ts`。

### 2.1 Cline

- **结束条件：看有没有配置「完成工具」。** 循环条件是 `this.config.maxIterations === undefined || this.state.iteration < this.config.maxIterations`（A 级，`agent-runtime.ts:850-851`）。模型这一轮没调工具时：如果工具集里有 `submit_and_exit`（`lifecycle.completesRun === true`），注入一条提醒并继续；否则直接 `finishRun("completed", finalAssistantMessage)`（`:962-977`）。调了 `submit_and_exit` 则运行完成（`:1018-1023`）。
- **默认交互入口并没有启用完成工具**：VS Code 插件的会话工厂写死 `maxIterations: undefined,`、`enableAgentTeams: false`（`apps/vscode/src/sdk/cline-session-factory.ts:1161,1175`）；工具预设 act／plan／search／minimal 都是 `enableSubmitAndExit: false`，只有 yolo 预设是 `true`（`sdk/packages/core/src/extensions/tools/presets.ts:34-107`）。所以默认交互使用中是「模型有一轮不调工具就结束」，和第 1 类主流一致。
- **催续（仅 yolo／团队模式）**：'[SYSTEM] This run is not complete until you call one of these terminal completion tools: submit_and_exit. Continue working if requirements are not met. If the task is complete, call the appropriate terminal completion tool now.'（`agent-runtime.ts:772-774`）。团队模式另有 '…Do NOT stop until all tasks are completed.'（`sdk/packages/core/src/runtime/orchestration/runtime-builder.ts:893`）。
- **输出被截断**：提醒 'Your previous response was cut off because it reached the model's output-token limit before finishing. Keep responses concise: take one small step at a time…'，连续最多 3 次（`MAX_TOKENS_RECOVERY_LIMIT = 3`，`agent-runtime.ts:72`），之后以终止消息 'Model reached the maximum output token limit before completing the turn' 结束（`:62`）。供应商错误重试 3 次（`PROVIDER_ERROR_MAX_RETRIES = 3`，`:87`）。
- **上限**：步数默认不限（见上）。连续可恢复错误上限 `config.execution?.maxConsecutiveMistakes ?? 6`（`sdk/packages/core/src/runtime/orchestration/session-runtime-orchestrator.ts:474`）；到连续错误上限时的停止消息是 'Stopped after N/6 consecutive mistakes (reason) at iteration M. … Session state was preserved. Send a new prompt to resume from the latest state.'（`sdk/packages/core/src/runtime/safety/mistake-tracker.ts:178-189`）。原地打转检测默认 `{ softThreshold: 3, hardThreshold: 5 }`（`sdk/packages/shared/src/agents/types.ts:278`，注释称 CLI 默认开启；VS Code 入口是否开启未核实），到硬阈值 'Detected repeated tool calls to `x`; stopping to avoid a loop.'（`session-runtime-orchestrator.ts:1552`）。超过 `maxIterations` 直接抛错 'Agent runtime exceeded maxIterations (N)'（`agent-runtime.ts:1039`）。
- **「implicit coercion」**：在 Cline 与 Roo-Code 的源码和 CHANGELOG 里都没找到这个名字的功能，未核实。最接近的现象是 Roo-Code 的「没调工具就注入错误提醒」（见下）。
- **提示词**：'IMPORTANT: Always includes tool calls in your response until the task is completed. Response without tool calls will considered as completed with final answer.'；'Always verify the files you have edited or created at the end of the task to ensure they are completed and working as expected.'（`sdk/packages/shared/src/prompt/system/act.ts`）；`submit_and_exit` 的工具描述：'Do not submit on the assumption that your solution works — submit because you have observed evidence that it does.'（`sdk/packages/core/src/extensions/tools/definitions.ts`）。

### 2.2 Roo-Code

- **结束条件：调用 `attempt_completion`，或模型有一轮不调工具。** 外层循环 `while (!this.abort)` 里，内层返回「没结束」就把 `formatResponse.noToolsUsed()` 作为下一条用户消息再发一轮（A 级，`src/core/task/Task.ts:2436-2458`）。
- **催续：每次没调工具都注入同一段话。** '[ERROR] You did not use a tool in your previous response! Please retry with a tool use. … # Next Steps / If you have completed the user's task, use the attempt_completion tool. / If you require additional information from the user, use the ask_followup_question tool. / Otherwise, if you have not completed the task and do not need additional information, then proceed with the next step of the task. / (This is an automated message, so do not respond to it conversationally.)'（`src/core/prompts/responses.ts:42-55`）。这段话本身没有次数上限；靠错误计数兜底：连续 2 次没调工具才计入错误（`Task.ts:3487-3493`），连续错误上限默认 3（`packages/types/src/provider-settings.ts:29` 的 `DEFAULT_CONSECUTIVE_MISTAKE_LIMIT = 3`），到顶弹窗问用户，用户回一句「继续」就把计数清零（`Task.ts:2483-2500`）。
- **完成被拦的两种情况**：本轮有工具调用失败时调用 `attempt_completion`，会收到错误而不是完成（`src/core/tools/AttemptCompletionTool.ts:43-44`）；设置项 `preventCompletionWithOpenTodos`（默认 false）打开时，有待办未完成则拒绝：'Cannot complete task while there are incomplete todos. Treat the current workspace, tool results, and durable session state as authoritative; inspect them instead of assuming earlier narration is still current. Make concrete progress and verify the result. Before claiming completion, gather evidence that the whole objective is achieved, read the current goal, and mark it complete. - **结束靠规则。** 模型标记完成或受阻后，本轮结束，系统注入一段收尾指令（`packages/goal/tool-goal/src/wrapup.ts`）。完成时：'The goal is marked complete and this autonomous run is ending. Write the closing message to the user now: state the outcome, summarize what was done and how it was verified, and point to the concrete results (files, commits, or other artifacts). … Do not call any more tools in this run; further work waits for the user's next instruction.' 受阻时要求写清「已完成什么、具体的受阻条件和尝试过什么、需要用户做什么」。收尾指令里还有一句防编造：'Report only what earlier rounds and tool results in this session actually establish; when a detail is not in the session, say so instead of inventing it.'
- **上限：只有轮数上限，默认 256 轮。** `defaultMaxGoalRounds: 256`，创建目标时可自带更小的上限（`packages/goal/goal/README.zh.md`）。轮数用尽时目标记为受阻，稳定代码 `round-limit`，随后走上面的受阻收尾。包说明明写「只有 Round 上限，不是资源预算」「只有 Round 数量预算——`maxGoalRounds` 不计量 token、货币、挂钟时间或提供方配额」。
- **续跑必须由人授权。** 会话恢复或 fork 之后，活跃目标的续跑是停用的，「在有人显式 resume 之前，agent 不会自行继续」；驱动器说明：「驱动器绝不会自行复活工作」「取消绝不会自动重启 Round」。
- **出错后怎么修**：异常情况不自动重试（「暂时性的提供方与持久化失败需要之后由用户授权 resume」）；只有上下文溢出走「先剪枝工具结果、再摘要」后重试（`docs/agent-lifecycle.zh.md`）。
- **防打转的小提醒（默认开，只提醒不拦截）**：同一个工具、同样参数连续重复到第 3、5、8 次时，提醒模型检查上一次结果并改变方法或结束任务（`packages/guard/repeat-tool-reminder/README.zh.md`）。
- **它自己写明的缺口**：「没有独立评估器——面向模型的 goal 策略会判断证据是否足以完成……评估器支持的认证仍保持暂缓」；「阻塞条件是否相同仍由模型判断」（驱动器与工具两个包说明的「已知限制」）。
- **提示词里关于「做完」的句子**：可引的是上面的目标策略章节与续跑模板；主系统提示词里的成文句子未找到，未核实。（2026-11-23 补充核实：主系统提示词为空——基础组合包对 `personaPrefix` 显式配了空串，注释写明「deployment persona 是部署选择」，见 `packages/bundle/base/cordis.patch.yml`；因此 DSH 默认没有任何「完成前验证」类提示句。）

## 6. 闭源产品：Claude Code 与 Cursor（仅官方文档，2026-11-23 抓取）

### 6.1 Claude Code

- **结束条件：模型有一轮不再调用工具。** Agent SDK 文档：「Claude continues calling tools and processing results until it produces a response with no tool calls.」「Turns continue until Claude produces output with no tool calls, at which point the loop ends and the final result is delivered.」（A 级，<https://code.claude.com/docs/en/agent-sdk/agent-loop>）
- **催续一：停止钩子可以强制继续，并有两道防死循环。** `Stop` 事件「Runs when the main Claude Code agent has finished responding.」；返回 `decision: "block"` 加 `reason`（或退出码 2，stderr 作为理由）即「prevents Claude from stopping」，对话继续（<https://code.claude.com/docs/en/hooks>）。防死循环：①输入里的 `stop_hook_active` 字段「is true when Claude Code is already continuing as a result of a stop hook. Check this value … to avoid blocking on a condition that will never resolve.」；②「Claude Code applies an 8-consecutive-continuation cap: after stop hooks have continued the turn eight times in a row, Claude Code overrides the next block and ends the turn. The count of consecutive continuations resets each time Claude calls a tool. To raise the cap, set `CLAUDE_CODE_STOP_HOOK_BLOCK_CAP`.」指南页写明症状：「Claude keeps working instead of stopping, then ends the turn with a warning that the Stop hook blocked too many consecutive times.」（<https://code.claude.com/docs/en/hooks-guide>）
- **催续二：钩子可以直接让模型当裁判。** 「prompt 型」停止钩子把对话交给一个模型判断，返回 `ok`／`ok: false`／`impossible`；「Stop and SubagentStop: the reason is fed back to Claude as its next instruction and the turn continues, unless the response also sets `impossible: true`, in which case Claude Code allows the stop and the turn ends.」另有实验性的「agent 型」钩子，起一个最多 50 轮的子代理去实际核实（如跑测试）再裁决（同上 hooks 页）。
- **催续三：内置 `/goal` 命令。** 「The `/goal` command sets a completion condition and Claude keeps working toward it without you prompting each step. After each turn, a model checks whether the condition holds. If the model judges it not yet met, Claude starts another turn instead of returning control to you.」裁决三种：未达成／达成／不可能。防打转：「If Claude keeps answering the evaluator without making progress (no tool use for several turns in a row), Claude Code stops the loop, prints a warning, and returns control to you with the goal still set.」限轮数的办法是写进条件里：「To bound how long a goal runs, include a turn or time clause in the condition, such as `or stop after 20 turns`.」审核者「doesn't run commands or read files independently」，只看对话里已经出现的结果；需要人工介入的错误会清掉目标，其余错误「After three automatic retries, the goal pauses instead.」（<https://code.claude.com/docs/en/goal>）
- **上限**：命令行 `--max-turns`「Limit the number of agentic turns (print mode only). No limit by default.」（<https://code.claude.com/docs/en/cli-reference>）；Agent SDK `max_turns`／`maxTurns` 默认无、另有 `max_budget_usd`，到顶返回 `error_max_turns`，文本 'Reached maximum number of turns'，进程以非零码退出（agent-loop 页）。
- **提示词**：闭源，系统提示词不公开，未核实。文档里可引的一句：「Auto mode on its own approves tool calls within a single turn but doesn't start a new one. Claude stops when it judges the work done.」（goal 页）

### 6.2 Cursor

- **结束条件：官方文档没有明写判定条件，未核实。** 钩子文档只说 `stop` 事件「Called when the agent loop ends.」（A 级，<https://cursor.com/docs/hooks>）
- **催续：`stop` 钩子可以自动续接，默认最多 5 次。** 钩子输入含 `status`（completed／aborted／error）和 `loop_count`；输出 `followup_message`：「When provided and non-empty, Cursor will automatically submit it as the next user message. This enables loop-style flows (e.g., iterate until a goal is met).」「The default limit is 5 auto follow-ups per script, configurable via the `loop_limit` option. Set `loop_limit` to `null` to remove the cap.」子代理的 `subagentStop` 同理。官方示例：状态为 error 且连续失败 2 次、`loop_count < 4` 时自动重试。另有「prompt 型」钩子（模型返回 `{ ok, reason }`）。注意 `followup_message`「Only consumed when `status` is `"completed"`」（`subagentStop` 一节的说明；`stop` 的说明未单独写明，按同构推定）。
- **上限**：「There is no limit on the number of tool calls Agent can make during a task.」（<https://cursor.com/docs/agent/overview>）；命令行参数页没有列出任何轮数上限选项（<https://cursor.com/docs/cli/reference/parameters>）。
- **验证环节**：Agent Review 是事后的代码评审——「runs a dedicated code review on your local changes」「You can set it to run automatically after every agent task, or leave it manual and trigger it yourself.」（<https://cursor.com/docs/agent/agent-review>），不是完成前的闸门；评审结果是否回灌给模型继续修，未核实。浏览器工具用于「test applications, and verify visual changes」（agent/overview）；调试模式的最后一步是「Verify and clean up: You can re-run the reproduction steps to verify the fix.」（<https://cursor.com/docs/agent/debug-mode>）。

## 8. 对「一次网页应用生成 run 该怎么结束」最相关的几点

以下是从证据里直接能读出的几条，供决策取用，不代表唯一做法。

1. **「停下来就重发一句固定的话」在样本里是孤例，各家自动催续都满足「有触发条件、带信息、有上限或止损」。** 对照：OpenHands 的续接带「Outstanding: …」（`goal/prompts.py`）、bolt.diy 的闸门带具体缺项（`agentLoop.ts:282-299`）、Cursor 的续接默认 5 次（hooks 文档）、Claude Code 的停止钩子连续 8 次即放行（hooks 文档）。两个最接近本平台的也都有止损：Roo-Code 靠连续错误上限 3 次后问用户；DeepSeek Harness 靠轮数上限（默认 256）、「同一障碍连续 3 轮才能报受阻」和人授权。本平台那条消息在实测里既没让模型多做实事（「做完了」25–48 次），又占了过半时长，和这些做法的差距在于：不区分「模型确实做完了」和「模型偷懒」，也没有「这次催了还是没进展就别催了」的止损。
2. **和本平台最同类的是 bolt.diy Agent Mode，它把「完成」做成了服务端闸门，判据和本平台的验收口径几乎一一对应。** 要求有计划、跑过应用、最近修改后有通过的检查、预览在跑，不满足就把缺项回给模型，到 32 步上限就关工具要模型如实汇报（`app/lib/common/agentLoop.ts`、`app/lib/.server/llm/agent-loop.ts`）。本平台的「PRD 全部功能＋8081 起服务」正好可以落成同样的几条可核对项（服务是否在 8081 监听、冒烟检查是否通过、需求清单是否逐条有证据）。
3. **「另起一个模型当审核者」是四家（OpenHands、Codex、OpenCode、Claude Code）已经做出来的形态，提示词写法可以直接借鉴。** 共同点：只认对话里的工具结果／命令输出，「模型说做完了」不算证据（OpenHands 'merely-claimed-but-unverified evidence as NOT satisfied'；OpenCode 'The assistant claiming the goal is met is not evidence… When in doubt, answer "continue"'）；催续时写明还差什么；有轮数上限和「没进展就停」；「受阻」要同一原因重复至少 3 轮才能判（Codex 模板）。Claude Code 文档还点明了它和「自动批准工具」的分工：后者只管一轮之内不弹窗，前者才管一轮结束后要不要再来一轮。
4. **上限到顶时，「关掉工具、让模型写一份如实总结」比直接报错更常见，而且能给出「完成／受限／受阻」三种明确收尾状态。** OpenCode 的 MAX_STEPS_PROMPT、bolt.diy 的 `limited`／`blocked`、Goose 的「Would you like me to continue?」都是这个路数；直接报错的是 OpenHands、Claude Code、mini-swe-agent。对本平台来说，这意味着「撞轮数上限」不必是 run 失败，可以是一次带「已完成／未完成清单」的正常收尾。
5. **「连续两次不带工具才算结束」在样本里没有结束条件上的对应物。** 各家是「一次不带工具即结束」或「必须显式提交」；最接近的是 Roo-Code 把「连续 2 次没调工具」计为一次错误（计错，不是结束）。对冲模型过早收工的办法是审核者或闸门（见第 2、3 点），不是数次数。本平台的「两次」如果本意是对冲偷懒，证据指向换一种对冲方式更有效。
6. **出错后自动修，各家都不在框架层单独设上限，而是并入总步数或费用上限，靠提示词约束「失败就修、修完重跑」。** 便宜而有效的防打转做法是 OpenHands 的「同参数同错误 3 次才提示、只提示一次」（`stuck_detector.py`）和 bolt.diy 的「修改之后旧的通过结果作废、必须重跑」（`stream-text.ts:237`）——后者正好对应「改完没重新起服务就说做好了」这类问题。
7. **参照系统 DeepSeek Harness 对同一个问题的答案，是把「续跑」做成有额度的轮次，并把收场写成规则。** 续跑提示里写明「第几轮／共几轮」；完成要模型显式标记，且「宣称完成前先取证整个目标达成」；「难、不确定、还有活没干」不算受阻，同一障碍连续 3 轮才能报受阻；标记完成或到上限后，系统按规则要模型写收尾说明（做了什么、怎么验证的、哪些要用户看；受阻时写清做到哪、卡在哪、要用户做什么），不许再调用工具；轮数用尽记为「受阻」而不是失败，人可以授权再跑（§5.5）。Codex 的目标续跑是同一套形态：工具同名 `create_goal`／`update_goal`，受阻规则同文（`codex-rs/ext/goal/templates/goals/continuation.md`）。
8. **参照系统自己也没解决「模型说做完了算不算数」。** DeepSeek Harness 在包说明的「已知限制」里写明「没有独立评估器」，证据够不够仍由模型判断。样本里把「说做完了」变成可核对事实的只有两种现成形态：服务端核对过程事实（bolt.diy Agent Mode 的闸门），或另起一个模型当审核者（OpenHands、OpenCode、Claude Code）。
