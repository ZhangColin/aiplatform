# 报价呈现入对话流：报价卡视镜语义

订单报价长期对用户无感（在线仅一条瞬时 toast、回访时订单 tab 不自动挂载、改价完全静默）。决定：首次报价与改价都在对话区落报价卡——平台对用户的发言，与问答卡、收尾卡同族；卡为**视镜非快照**——落库仅事件（报价已出 / 报价已更新）与订单引用，金额与状态渲染时取订单当前态；改价追加新卡不改旧卡；卡内即支付闭环，订单 tab 保留完整详情与改价历史的家。感知配比：对话区报价卡是主感知面，项目列表与首页只作路标（状态徽标不带金额），平台通知只作信号（SSE 载荷不含金额、详情走查询）。

## Considered Options

- **快照卡**（落库冻结金额，改价追加新卡并把旧卡标注「已被取代」）：被否。旧金额残留对话流会误导支付决策；「只追加不改写」的历史定格语义适用于收尾卡（记录一轮做了什么），不适用于「现在该付多少钱」——后者是当前事实而非历史瞬间。视镜与平台既有原则对齐（通知只作信号、状态以查询为准），且已支付/已取消/已归档转态零追加成本。
- **订单自成一面，他面只做路标**（报价只住订单 tab，对话区不出卡）：被否。用户与对话区朝夕相处，平台最正式的一次发言（钱的事）却藏在需手动加挂的 tab 里——正是本线要修的病根。
- **改价维持静默**（「改价不换状态不发事件」的现状）：被否。状态机洁癖不敌体验裸洞——改价留痕只有用户主动打开订单 tab 才可见，留痕意义落空；改价与首次报价在用户面是同一类事：平台动了你的钱数。
- **通知中心 / 未读收件箱**：被否（「平台通知」词条明确 _Avoid_ 通知中心）。跨项目感知以「订单状态 = 项目的状态属性」渗透到首页与列表的项目卡实现，不建独立通知面。

## Consequences

- 对话史 schema 演进：新增报价卡 kind 与一个 quote jsonb 载荷列；append-only 纪律不变，写口仍归对话史写服务（recordGuide 先例）。
- 报价卡与 SSE 信号均不含金额，渲染依赖订单详情查询——在 SSE 按用户隔离缺陷修复前不扩大暴露面（隔离缺口另票跟踪）。
- 下单成功不建对话卡：用户自己发起的动作平台不回告；待报价期间的回访呈现靠订单 tab 自动挂载。
- 站外触达（邮件/短信）v1 不做；报价产生与改价已是明确事件点，将来接通知渠道为顺挂。
