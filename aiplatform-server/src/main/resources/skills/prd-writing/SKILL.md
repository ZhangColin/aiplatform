# PRD 写作技能

平台替用户梳理的需求文档撰写规范：面向非技术用户可读，固定七章节依序为——需求背景、目标用户、核心场景、范围边界、关键约束、清单章、验收与待确认。

补全呈现口径（#461 新访谈策略）：访谈期对非必答缺口平台以补全直接决定，补全集中呈现在 PRD——直接写进相应章节的正文叙述（专业身份直陈决定本身，如「登录方式采用手机号验证码登录」），是确定的专业判断，不用「假设/如果/我猜」字眼、不自问自答；PRD 全文不区分用户答的与平台补的，不另设补全清单或标记。

清单章按项目终点类型走形（终点类型用 query_project_facts 查询；平台请求切换时会直接告知）：

- 系统形（终点类型＝系统、系统＋设计）：章节名「功能清单」——系统生成的直接依据：编号列出系统的页面与功能点，每点附验收要点（做成什么样算合格）。系统＋设计项目不另立设计清单：设计范围＝本清单页面集（平台告知过作用域的以告知为准），设计硬约束（系统构建遵循本项目定稿设计）写入「关键约束」章。
- 设计形（终点类型＝设计）：章节名「设计物清单」——设计过程的直接依据：编号列出各设计物，每件附用途、尺寸、风格要点与验收要点。
- 终点类型变更后修订 PRD 时，清单章必须随改到新形态（其余章节按新终点的交付语境相应梳理）。

「验收与待确认」章保留但不再拦门（#462 去确认门——确认动作整段退役，本章条目不拦任何动作，只作呈现）：只收补全后仍无法决定、又不挡核心流程的缺口——缺了会建错方向的缺口是访谈期必答题，应经 ask_user 问掉、不进本章；收敛令后的未决缺口一律按推荐补全，也不进本章。章内平铺编号列条目（#462 起不再分两级、不设拦截级分组子标题——存量 PRD 里的旧分组标题平台解析时仅作界标容忍），每条开头用【维度】标注所属维度，维度词表固定五个：目标与角色、主流程、功能与边界、数据与约束、验收，并写明所缺信息与建议口径（如「【数据与约束】列表默认排序偏好未确认，建议按创建时间倒序推进」）；没有任何缺项则整章写「暂无」。

全文用平实语言写给非技术用户读：不堆术语、不用技术黑话，用户能逐块看懂。
